## Summary

Host special: Ridd shares his personal four-quadrant mental model for picking AI coding tools as a designer. X-axis = size of work (quick P3 bug fix ↔ zero-to-one meaty idea). Y-axis = how much material already exists in production (blank slate ↔ iterating on shipped). Canvas is still useful for unshaped early work — he rejects the "canvas is dead / everything in code" hype; writing and mess on a canvas come before code when the problem isn't shaped yet.

Bottom-left (small, focused AI prototypes): three tools. **Figma Make** when UI already exists (Inflight publish-flow progress/jiggle component; Figma plugin success animation shipped to prod within the hour — URL dropped on canvas for handoff). **Lovable** for blank/larger prompt runs (Vibe slider POC for Bartech/Rive; Lottie/Rive + Jitter hover cards that landed in production). Trap: rebuilding production outside the codebase / sweating pixels off the design system (he admits doing this in Lovable). **Devin** as newcomer — single-input speed like Lovable but connected to the Inflight design system + codebase so styles/components stay live.

Biggest recent shift: Opus 4.5 + Claude Code making production PRs easy at a startup pace. Tried Warp + GitHub Desktop, then Claude Mac app; now **Conductor** dominates — parallel Claude Code worktrees so he stays in flow instead of waiting every two minutes. Demos Linear-batched Inflight fixes (research pin-on-canvas history; version title character limit; autofocus Add comment), dictate prompts, Command-Shift-R code-review agent, Command-R local preview, then open PRs.

Top-right meaty work: Claude Mac app as **"CTO"** — plans (e.g. personal OS "Radar"), writes Conductor prompts, evaluates agent reports; same pattern on larger Inflight features that touch backend. Emphasizes this is personal practice, not universal; expects a part two.
